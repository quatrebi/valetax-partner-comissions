# Valetax Commissions App (Interview Test Task)

Примерное время разработки около 2-х дней, не включая времени на изучение материалов.

## Как запустить

Необходим .NET 10 и выше и Docker.

На выбор предлагаю два способа:
* `docker-compose.yaml` - классический способ, поднимает весь стек. А также Aspire Dashboard отдельно вместо других сервисов (Grafana, Jaeger, Seq и т.д.);
* `Aspire` - аналог "компоуза" от Microsoft. Также поднимает весь стек, но при этом предоставляет UI для просмотра сервисов, логов, метрик, трейсов и т.д.

### Docker Compose
```bash
docker compose up --build
```
| Сервис | Адрес |
|---|---|
| Partners API | http://localhost:5003/scalar |
| Wallets API | http://localhost:5264/scalar |
| Valetax API | http://localhost:5274/scalar |
| Логи, метрики, трейсы | http://localhost:18888 |

### Aspire
`dotnet run --project src/Valetax.Aspire` — дашборд откроется на http://localhost:15000.

### Unit-tests
`dotnet test ValetaxPartnerCommissions.slnx`

## Конфигурация
* `CommissionRounding:Mode` - настройка округления. `ToNegativeInfinity`
* `CommissionPayout:PollingInterval` - как часто запускается фоновая задача по выплатам. `00:00:05`
* `PartnerTree:MaxDepth` - настройка глубины дерева. `10`

## Архитектура
Приложение распределено на доменные зоны, и под каждую доменную зону свой проект/микросервис:
* `Valetax.Infrastructure` - общий проект для унификации всех микросервисов. Включает в себя подключение необходимых зависимостей, таких как:
  * `OpenTelemetry` - для логов, метрик и трейсов;
  * `MassTransit`, `MassTransit.Kafka` - для подключения Kafka-брокера;
  * `Quartz` - для подключения background-tasks;
  * `MinimalApi` - auto-inject `IApiEndpoint` для использования стиля MinimalApi;
  * `IValetax*Setup` - auto-inject необходимых настроек для `IOptions`-паттерна, Kafka-producers, а также Quartz-jobs;
* `Valetax.Partners.Api` - микросервис для взаимодействия с клиентами. Предоставляет CRUD для управления клиентами, а также получение древа реферальной программы
  * `Valetax.Partners.Api.Contracts` - контракты, но по сути хранит интеграционный ивент, чтобы его видели другие микросервисы;
  * `Valetax.Partners.Api.Grpc` - gRPC-контракты для интеграций зависимых микросервисов;
* `Valetax.Wallets.Api` - микросервис с CRUD для управления кошельками клиентов, а также сохранение пришедших им комиссий
  * TL;DR - `*.Grpc` проект аналогично выше;
* `Valetax.Api` - корневой бизнес-проект, по сути является Facade-service над двумя другими. Обрабатывает события, а также рассчитывает комиссии;
  * **Спортивная травма:** алгоритм для вычисления числа Фибоначчи использует матрицы для более быстрого расчета для больших чисел, хотя для тестового задания справляется и обычная логика, т.к. древо имеет ограничение до 10 вложений;
* `Valetax.Api.Tests` - Unit-тесты для расчета комиссий

Синхронное микросервисное взаимодействие происходит исключительно по gRPC-протоколу. Асинхронное через брокер Kafka + outbox;
Остальное взаимодействие предполагает наличие frontend-проекта, поэтому оставлены REST-endpoints;

### Разъяснение принятых решений
Доменные зоны были разбиты исходя из предположительного роста проекта.
Если взять этот проект масштабнее, то куда проще и удобнее разбить отдельно на `Partners.Api`, `Wallets.Api` и `Commissions.Api`.
Такая модель позволяет горизонтально масштабировать проект и добавлять мощности под конкретный домен, а также поменять логику начислений комиссии и при этом не изменять логику для других сервисов.

Исходя из этого, для синхронизации Partner -> Wallet выбрасывается `PartnerCreatedIntegrationEvent`, чтобы уведомить остальную часть системы о создании нового пользователя.
В свою очередь `Wallets.Api` создаёт кошелёк, а `Commissions.Api` может также сохранить его у себя и сделать какие-либо доп. расчёты.

Как уже было описано ранее `Commissions.Api` - это фасад. Он вызывает остальные микросервисы для валидации, а после начисляет комиссию через `Wallets.Api`.
При этом `Partners.Api` участвует минимально. Если приложение не сможет создавать новых пользователей, то логика по начислению для **уже существующих** все ещё продолжит работать.

Для консистентности данных и раннего выхода из HTTP-запроса был добавлен Outbox-паттерн и соответствующие Jobs.
Jobs в фоне обрабатывают создание пользователей для других микросервисов и расчёт начисления по уже созданным событиям, что в свою очередь не блокирует клиентские HTTP-запросы.
Также этот паттерн можно было реализовать через связку DomainEvents + DbInterceptors, но уже не стал усложнять проект с инфраструктурой.

При создании события сервис делает условный слепок текущего состояния: получает дерево пользователей, сохраняет у каждого статус, тип логики по выплате комиссий и прочее.
Это необходимо, чтобы при изменении данных старые выплаты рассчитывались по старому типу. А также чтобы новые рефералки не смогли получить старую комиссию.
После в фоне для каждой рефералки высчитывается комиссия, пополняется кошелёк и записывается её статус. При ошибке запись пропускается до след. прогона, и при повторной обработке повторяется снова, за исключением уже проведенных выплат.

### Используемые пакеты
>  **TL;DR** Данные пакеты для меня привычная практика, поэтому и использовал их

* `FluentValidation` - пакет для описания валидаторов Fluent-подхода. Интегрируется через `AddEndpointFilter` для MinimalApi;
* `Quartz` - механизм для запуска background-tasks. По сути убирает обертку для скоупа в `BackgroundService`-классе;
* `Microsoft.AspNetCore.OpenApi` & `Scalar UI` - аналог Swagger, рекомендации Microsoft на переход Scalar UI + их библиотеки по OpenApi;
* _остальные пакеты были описаны выше_

## Отказоустойчивость
Для отказоустойчивости используется стандартная практика у Microsoft - пакет `Microsoft.Extensions.Http.Resilience`, который в свою очередь уже предоставляет паттерны _Retry_ и _Circuit breaker_;

_Graceful shutdown_ был настроен как на docker-side стороне, так и внутри приложения, чтобы фоновые задачи сначала закончили обработку, сохранились и после этого приложение закрылось.

Каждый запрос идемпотентен, при наличии уже существующего объекта возвращается из базы данных. Повторная выплата не производится, возвращается `AlreadyPaid`.

Микросервисы реализуют встроенный HealthChecks-паттерн `/health` + `/alive`.

## Метрики
Добавлены стандартные метрики для стека через OpenTelemetry (ASP.NET, HttpClient, Runtime, Npgsql, MassTransit). А также бизнес-метрики:
* `valetax.profit_events.accepted` - кол-во принятых событий
* `valetax.commissions.accrued` - кол-во комиссий по событию, нулевые не считаются
* `valetax.commissions.paid` - кол-во комиссий **выплаченных** на кошелёк. `AlreadyPaid` не учитываются
* `valetax.commissions.payout_failures` - неудачные попытки выплат с `reason`
* `valetax.profit_events.oldest_pending_age` - сколько ждёт самое старое событие с невыплаченными комиссиями
